## 1. OpenCode

### 1.1 Что есть что

Три разные вещи, которые нельзя смешивать:

1. **opencode CLI** — открытый агент для терминала, репозиторий
   [github.com/anomalyco/opencode](https://github.com/anomalyco/opencode)
   (канонический репозиторий, на него ссылается сайт документации).
   Сам по себе платным сервисом не является и счёта не имеет.
2. **OpenCode Zen** — платный шлюз моделей, отдельная регистрация, отдельный
   биллинг, **pay-as-you-go кредит** (кошелёк в USD).
   [opencode.ai/docs/zen](https://opencode.ai/docs/zen/)
3. **OpenCode Go** — **подписка $10/месяц** с лимитами использования по моделям.
   [opencode.ai/docs/go](https://opencode.ai/docs/go/)

Zen и Go — разные механики оплаты, не два имени одного счёта. Go — квоты в рамках
подписки; Zen — денежный кредит. Связаны опционально: при исчерпании лимитов Go
в консоли можно включить **Use balance**, и потребление пойдёт с кредита Zen.
«Остаток Go» и «остаток Zen» — независимые величины, одна из другой не выводится.

### 1.2 Документированные endpoints

Официальная документация описывает **только inference**:

Zen ([opencode.ai/docs/zen](https://opencode.ai/docs/zen/)):
```
https://opencode.ai/zen/v1/responses          (OpenAI-совместимые)
https://opencode.ai/zen/v1/messages           (Anthropic-совместимые)
https://opencode.ai/zen/v1/chat/completions   (OpenAI-совместимые сторонние)
https://opencode.ai/zen/v1/models/{model-id}  (Google)
https://opencode.ai/zen/v1/models             (список моделей)
```

Go ([opencode.ai/docs/go](https://opencode.ai/docs/go/)):
```
https://opencode.ai/zen/go/v1/responses
https://opencode.ai/zen/go/v1/chat/completions
https://opencode.ai/zen/go/v1/messages
```

Документация Go отсылает к веб-консоли: «You can track your current usage in the
console» — без указания программного доступа.

### 1.3 Квота Go: маршрут есть в исходниках консоли

В открытых исходниках консоли присутствует маршрут статуса квоты Go:
[`packages/console/app/src/routes/zen/go/v1/usage.ts`](https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/console/app/src/routes/zen/go/v1/usage.ts)
(ветка `dev`, прочитан 12 сентября 2026). По расположению файла маршрут
соответствует `GET /zen/go/v1/usage`.

Из кода: аутентификация тем же ключом — `Authorization: Bearer <apiKey>`
(разбор регулярным выражением `/^Bearer (\S+)$/`). Форма ответа:

```
{ usage: { rolling: { status, percent, resetsAt },
           weekly:  { status, percent, resetsAt },
           monthly: { status, percent, resetsAt } } }
```

`status` — `"ok" | "rate-limited"`, `percent` — процент использования,
`resetsAt` — ISO-время сброса окна. При отсутствии подписки маршрут отвечает 403
«OpenCode Go subscription required».

**Что это НЕ даёт.** Это статус **квоты подписки Go** и ничего больше:

- **не кошелёк Zen** — баланса кредита здесь нет;
- **не account-wide расход в USD** — денежных сумм в ответе нет вообще;
- проценты окон нельзя пересчитать ни в доллары, ни в остаток кредита.

**Чем это НЕ является методологически.** Файл в репозитории — это исходный код,
а не опубликованный контракт. Из него не следует, что маршрут:
поддерживается как публичный API, стабилен между версиями, доступен на
работающем сервисе, и что его форма не изменится без предупреждения.
Ставить на него продуктовую функцию без подтверждения от поставщика —
опора на ненаблюдаемое обещание.

### 1.4 Поддерживаемый billing API: в проверенной документации не найден

Для кошелька Zen и для account-wide расхода в USD **поддерживаемого billing API
в проверенной официальной документации не найдено**.

Существует открытая пользовательская заявка

Это **запрос пользователя, а не заявление поставщика**. Её содержание —

я **не проверял по первичным источникам** и за факты не выдаю.

Также в поиске присутствует более ранняя заявка

### 1.5 Баланс против локальных токенов и оценок

Для контракта Spender («стоимость, баланс и токены имеют независимые доступность
и происхождение»):

- usage по токенам в ответах inference — **локальное наблюдение**, дающее только
  **оценку** потраченного этим клиентом;
- оценка **не баланс** и **не account-wide расход**: она не видит трат из других
  клиентов, из веб-консоли, с других машин;
- перевод токенов в деньги требует локальной таблицы цен — вторая оценка поверх
  первой, и по правилам проекта показывать её как официальную метрику нельзя.

### 1.6 Credential

Ключ создаётся в консоли (`opencode.ai/auth` → Create API Key) и вставляется
в TUI при `/connect`. Для маршрута квоты Go в исходниках видно
`Authorization: Bearer`. Для inference-endpoints Zen точный заголовок и имя
переменной окружения на прочитанных страницах документации не указаны —
см. «Непроверенное». Понятия scopes или read-only ключей для Zen/Go
в документации не встречается.

## 2. xAI

### 2.1 Два разных ключа

| | Inference key | Management key |
|---|---|---|
| База | `https://api.x.ai` | `https://management-api.x.ai` |
| Заголовок | `Authorization: Bearer <API key>` | `Authorization: Bearer <Management API Key>` |
| Где создаётся | Консоль xAI, API Keys | Консоль xAI, **Settings → Management Keys** |
| Что умеет | вызовы моделей | администрирование, биллинг, аудит — в пределах своих ACL |
| Даёт баланс/расходы | **нет** | **да** |

Источник: [Using Management API](https://docs.x.ai/developers/management-api-guide).
Документация прямо говорит, что management key «separate from your API key».

### 2.2 Баланс — доступно

```
GET https://management-api.x.ai/v1/billing/teams/{team_id}/prepaid/balance
Authorization: Bearer <Management API Key>
```

Пример ответа из [официального reference](https://docs.x.ai/developers/rest-api-reference/management/billing):

```json
{
  "changes": [
    {
      "teamId": "65c1e471-205f-4566-9c5a-07198bcdf4ce",
      "changeOrigin": "PURCHASE",
      "topupStatus": "SUCCEEDED",
      "amount": { "val": "-1000" },
      "invoiceId": "7v7blf6c1G2g34OdI4N5tD1CKCdag4ZYLhn5vTBLIMM=",
      "invoiceNumber": "062-446-653-166",
      "createTime": "2025-02-24T15:28:02.308840Z",
      "paymentProcessor": { "kind": "STRIPE" }
    }
  ],
  "total": { "val": "-1000" }
}
```

**Единицы и знак — три отдельные ловушки:**

1. **Не USD, а центы.** `amount.val` документирован как «Representation of USD
   Cents». `"-1000"` — это 10.00 USD.
2. **Строка, а не число.** Парсить как целое число центов, не как `Double`.
3. **Знак инвертирован относительно интуиции.** При пополнении «amount field will
   be negative», `changeOrigin: "PURCHASE"`.

Ответ — журнал изменений (`changes`) плюс `total`. В примере единственное
изменение равно `total`, поэтому из примера нельзя заключить, означает ли `total`
остаток к использованию или сумму изменений. Это настоящая неясность —
см. «Непроверенное».

### 2.3 История расходов — доступно

```
POST https://management-api.x.ai/v1/billing/teams/{team_id}/usage
```

Принимает `timeRange` (`startTime`, `endTime`, `timezone`), `timeUnit`
(например `TIME_UNIT_DAY`), `values` с агрегациями (`AGGREGATION_SUM`,
`AGGREGATION_AVG`, `AGGREGATION_COUNT`), `groupBy`, `filters`.

Фрагмент примера ответа:

```json
{
  "timeSeries": [
    { "group": ["Chat grok-4-0709"],
      "dataPoints": [ { "timestamp": "2025-10-01T00:00:00Z", "values": [0.75973725] } ] },
    { "group": ["grok-2-image-1212"],
      "dataPoints": [ { "timestamp": "2025-10-03T00:00:00Z", "values": [0.14] } ] }
  ],
  "limitReached": false
}
```

**Единица здесь другая: доллары США дробным числом**, не центы и не строка.
В пределах одного API две денежные величины имеют разные единицы и типы —
смешивать их нельзя.

Ряд разбит по моделям и типам вызова. Флаг `limitReached: true` означает, что
ряд обрезан и суммировать ответ как полный нельзя.

Величина относится к команде (`team_id`), то есть это **account-wide** расход.

### 2.4 Прочие биллинговые endpoints

```
GET  /v1/billing/teams/{team_id}/billing-info
POST /v1/billing/teams/{team_id}/billing-info
GET  /v1/billing/teams/{team_id}/invoices
```

Для Spender релевантны `prepaid/balance`, `usage` и, возможно,

### 2.5 ACL: что именно позволяет конкретный ключ — открытый вопрос

Документация
[Accounts and Authorization](https://docs.x.ai/developers/rest-api-reference/management/auth)
описывает поле `acls` management-ключа дословно так:
**«ACLs of this key (controls what APIs can be accessed using the key).»**

Отсюда следует существенное уточнение: **права management-ключа определяются его
ACL, а не самим фактом принадлежности к классу management-ключей.** Утверждать,
что любой такой ключ обязательно умеет `prepaid/top-up` или удаление API-ключей,
оснований нет — это зависит от выданных ACL.

Что при этом **не установлено**:

- **минимальный набор ACL, достаточный для чтения `prepaid/balance` и `usage`**,
  в проверенной документации не описан;
- примеры ACL в документации (`api-key:model:*`, `api-key:endpoint:chat`,
  `api-key:endpoint:image`) относятся к inference-ключам; ACL-значения для
  биллинговых маршрутов не приведены;
- существует ли ACL-конфигурация, дающая только чтение биллинга без записи,
  из документации не видно.

Это **вопрос к поставщику или к живой проверке**, а не установленная небезопасность.
Практический вывод для Spender: перед сохранением ключа приложение может показать
пользователю его фактические ACL — см. 2.6.

### 2.6 Проверка ключа и получение team_id

```
GET https://management-api.x.ai/auth/management-keys/validation
```

**Без префикса `/v1`** — в отличие от биллинговых маршрутов. Возвращает метаданные
ключа: `apiKeyId`, `scope`, `scopeId`, `acls`.

- `scope` — «Scope the key is associated with», enum `SCOPE_UNSPECIFIED`,
  `SCOPE_TEAM`, `SCOPE_ORGANIZATION`.
- `scopeId` — «ID of the scope the key is associated with».

Отсюда: **при `scope = SCOPE_TEAM` значение `scopeId` и есть team ID**, то есть
`team_id` для биллинговых маршрутов можно получить программно из этого же ответа.
При `scope = SCOPE_ORGANIZATION` `scopeId` — идентификатор организации, не команды,
и этот путь не работает. Документация даёт одно общее описание поля на оба enum,
поэтому различие выведено из семантики `scope`, а не процитировано дословно.

Ручной ввод `team_id` обязательным требованием **не является**. Консоль
(`https://console.x.ai/team/default/settings/team`) остаётся запасным способом —
в частности для организационного scope.

Тот же ответ даёт приложению возможность показать фактические ACL ключа
пользователю до сохранения.

### 2.7 Grok-подписка против API

Потребительский Grok (grok.com, X Premium / SuperGrok) и xAI API — разные продукты
с разными счетами. **Официального источника, дающего программный доступ к остатку
или расходу потребительской подписки, не найдено.**
[FAQ по биллингу API](https://docs.x.ai/console/faq/billing) описывает только
prepaid-кредиты и постоплатное выставление счетов для API и потребительских планов
не затрагивает. Management API работает в терминах `team_id` API-аккаунта;
оснований считать, что он показывает потребление Grok-подписки, нет.

## 3. Доступно / не найдено / непроверенное

### Доступно (подтверждено официальной документацией)

- xAI: `GET /v1/billing/teams/{team_id}/prepaid/balance` — **центы USD, строкой**,
  знак при пополнении отрицательный.
- xAI: `POST /v1/billing/teams/{team_id}/usage` — **доллары USD, дробным числом**,
  разбивка по моделям, флаг `limitReached`.
- xAI: `GET /auth/management-keys/validation` (**без `/v1`**) — `apiKeyId`, `scope`,
  `scopeId`, `acls`; при `SCOPE_TEAM` даёт `team_id` программно.
- xAI: база `https://management-api.x.ai`, заголовок `Authorization: Bearer`.
- xAI: права ключа определяются его ACL — «controls what APIs can be accessed».
- OpenCode: Zen и Go — разные платные продукты (кредит против квот подписки).

### Подтверждено в исходниках, но не как публичный контракт

- OpenCode Go: маршрут статуса квоты `GET /zen/go/v1/usage`,
  `Authorization: Bearer`, окна `rolling`/`weekly`/`monthly` с `status`,
  `percent`, `resetsAt`; денежных величин не возвращает; 403 без подписки Go.
  Источник — файл репозитория, не опубликованная документация.

### Не найдено в проверенной документации

- OpenCode Zen: поддерживаемый endpoint баланса кошелька.
- OpenCode Zen/Go: поддерживаемый endpoint account-wide расхода в USD.
- xAI: описание минимального набора ACL для чтения биллинга.
- xAI: документированная ACL-конфигурация «только чтение биллинга».
- Grok-подписка: программный доступ к остатку/расходу.

Во всех случаях это утверждение об **отсутствии в проверенных источниках**,
а не доказательство отсутствия как такового.

### Непроверенное (дополнительная документация либо согласованная live-проверка)

1. **Семантика `total.val` в `prepaid/balance`** — остаток к использованию или
   сумма изменений. Из единственного примера различить нельзя; влияет на знак и
   порядок числа в UI.
2. **Пагинация `changes`** — ограничение и курсор не выяснены; при длинной истории
   `total` может относиться к странице.
3. **Минимальный ACL для биллинг-чтения** и наличие read-only конфигурации.
4. **Стабильность и доступность** маршрута `GET /zen/go/v1/usage` на работающем
   сервисе; поведение вне ветки `dev`.
5. **Точный заголовок аутентификации inference-endpoints Zen** и имя переменной
   окружения.
6. **Поведение `limitReached: true`** в `usage` — как дочитать остаток ряда.
7. **Rate limits** биллинговых endpoints xAI.
8. Содержание issue #10448 — заявка существует, не открывалась.

## 4. Рекомендация для решения владельца

### OpenCode — не добавлять как источник баланса/расходов

Для кошелька Zen и для account-wide расхода в USD поддерживаемого способа в
проверенной документации нет. Подсчёт по токенам даёт оценку одного клиента и по
правилам проекта официальной метрикой быть не может.

Маршрут квоты Go (`GET /zen/go/v1/usage`) найден в исходнике; доступность на
сервисе не проверена. Он отвечает на другой вопрос: «сколько процентов окна подписки израсходовано»,
а не «сколько денег осталось». Если владельцу нужен именно этот показатель, это
отдельная продуктовая задача с отдельным решением, и её цена — опора на
недокументированный маршрут из исходников, который поставщик не обязан сохранять.

Разумный шаг без кода: следить за issue #44189 и вернуться к вопросу, если
появится опубликованный endpoint.

### xAI — провайдер уже есть; следующий шаг не код, а живая сверка

По локальной сверке координатора xAI в Spender **уже реализован**:
`ProviderRegistry.swift:113-125` — `available`, `isVisibleByDefault: false`;
`ProviderTargetFactory` подключает `XAIProvider`; пути validation и balance/usage
существуют. Это результат проверки координатора, я локальный код не ревьюировал.

Поэтому вопрос «добавлять ли второго провайдера» не стоит, и изменений архитектуры
это исследование не требует. Следующий шаг — **разрешённая владельцем live-сверка
установленной копии и реального ключа**: сравнить баланс и расходы с кабинетом
за одинаковый период, проверить разрешения. Один успешный ответ не гарантирует
проверку пагинации или `limitReached`: не встретившиеся сценарии остаются открытыми.

Решения, которые остаются за владельцем:

1. разрешить ли разовую live-сверку с реальным ключом (обязательное условие для
   любых дальнейших утверждений о числах);
2. какие сценарии live-сверки разрешены; существующая интеграция уже поддерживает
   баланс и расходы, изменение состава метрик владельцем не запрошено;
3. запрашивать ли у xAI, какой минимальный ACL достаточен для чтения биллинга.
